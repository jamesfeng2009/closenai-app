# HILT — Human-In-The-Loop 审批关卡

> 层级：流程控制层
> 定位：**三道强制关卡**，防止 AI 偏离方向、浪费工作

---

## 核心原则

```
AI 可以在关卡之间自由发挥，但每到关卡必须停下来等用户确认。
用户说"No" → 回到上一阶段重做，不允许跳过。
```

## 三道关卡

```
                    ┌──────────────┐
                    │  用户说"开始"  │
                    └──────┬───────┘
                           ▼
                 ┌─────────────────┐
                 │  brainstorming  │
                 │  + grill-docs   │
                 │  + domain-model │
                 └────────┬────────┘
                          ▼
              ╔═══════════════════════╗
              ║ 🔴 HILT Gate 1: SPEC ║
              ║ "方案对吗？可以开始写代码了吗？" ║
              ╚═══════════════════════╝
                    │         │
                  ✅ 通过    ❌ 不通过
                    │         │
                    ▼         └──→ 回到 brainstorming
           ┌──────────────┐
           │  tdd / 实现   │
           │  + subagent   │
           └──────┬───────┘
                  ▼
       ╔══════════════════════════╗
       ║ 🔴 HILT Gate 2: REVIEW  ║
       ║ "代码改对了吗？可以验收了吗？" ║
       ╚══════════════════════════╝
             │         │
           ✅ 通过    ❌ 不通过
             │         │
             ▼         └──→ 回到 tdd/实现
    ┌──────────────┐
    │  code-review │
    │  + verify    │
    └──────┬───────┘
           ▼
╔══════════════════════════════╗
║ 🔴 HILT Gate 3: DONE        ║
║ "全部完成了吗？可以提交了吗？"   ║
╚══════════════════════════════╝
      │         │
    ✅ 通过    ❌ 不通过
      │         │
      ▼         └──→ 回到 review/verify
  ┌──────┐
  │ 完成  │
  └──────┘
```

---

## Gate 1: SPEC 审批（brainstorming 之后，写代码之前）

### 触发时机
`closenai-brainstorming` 完成 HARD-GATE 自审后，用户确认方案才能进入实现。

### 审批内容

向用户展示：

| 展示项 | 内容 |
|--------|------|
| 功能边界 | 做什么 / 不做什么 |
| 数据模型 | 涉及哪些表、字段、索引 |
| API 契约 | 端点、请求体、响应体 |
| 边界条件 | 空状态、错误处理、极端情况 |
| 文件清单 | 预计修改/新建的文件列表 |

### 审批问题

```
"方案确认 — 以上设计是否符合你的预期？可以开始写代码了吗？"
选项：
  1. ✅ 通过，开始实现
  2. ❌ 需要调整（请说明哪里不对）
  3. ⏸️ 暂停，我先看看
```

### 不通过的处理

- 用户说明调整方向 → 返回 `closenai-brainstorming` 重新设计
- 只修改用户指出的部分，不推翻全部重来

---

## Gate 2: REVIEW 审批（代码实现之后，验收之前）

### 触发时机
`closenai-tdd` 实现完成 + `closenai-code-review` 自动审查通过后，用户确认代码改动。

### 审批内容

向用户展示：

| 展示项 | 内容 |
|--------|------|
| 改动摘要 | 修改了哪些文件、新增了哪些文件 |
| 测试结果 | 测试通过/失败数量 |
| 审查结果 | 🔴阻断级 / 🟡建议级 / 🟢赞美级 |
| 关键代码片段 | 核心逻辑的代码（非全部） |

### 审批问题

```
"代码审查通过 — 改动如上。确认可以进入验收阶段吗？"
选项：
  1. ✅ 通过，开始验收
  2. ❌ 有问题（请指出具体问题）
  3. 📝 先看看代码再决定
```

### 不通过的处理

- 用户指出具体问题 → 返回 `closenai-tdd` 修复
- 用户说"代码风格不对" → 返回重构阶段
- 用户说"少了某个功能" → 返回 `closenai-brainstorming` 补充设计

---

## Gate 3: DONE 审批（验收之后，标记完成前）

### 触发时机
`closenai-verify` 5 维度检查全部通过后，用户最终确认。

### 审批内容

向用户展示：

| 展示项 | 内容 |
|--------|------|
| 功能验证 | 功能是否符合 PRD 验收标准 |
| 测试覆盖 | 测试通过率 + 覆盖率 |
| 安全检查 | 无 SQL 注入 / XSS / 认证绕过 |
| 边界条件 | 空状态、错误处理已验证 |
| 部署影响 | 是否需要数据库迁移、环境变量变更 |

### 审批问题

```
"全部验证通过 — 最终确认：可以标记为完成了吗？"
选项：
  1. ✅ 完成，标记 done
  2. ❌ 还有问题（请说明）
  3. 🔄 先部署测试环境验证
```

### 不通过的处理

- 用户指出遗漏 → 回到对应阶段修复
- 用户要先部署测试 → 帮助部署，然后回到 Gate 3

---

## 快速模式（跳过关卡）

当用户明确说以下任一语句时，可以跳过对应关卡：

| 用户说 | 跳过 |
|--------|------|
| "不用确认，直接做" | Gate 1（SPEC） |
| "代码没问题，直接验收" | Gate 2（REVIEW） |
| "直接提交" | Gate 3（DONE） |

**但 AI 必须回复确认**："收到，跳过 Gate N 审批，直接进入下一阶段。"

---

## 禁止行为

- ❌ 在 Gate 1 未通过时开始写代码
- ❌ 在 Gate 2 未通过时说"完成了"
- ❌ 用户说"No"后继续推进（必须回到上一阶段）
- ❌ 跳过 Gate 展示内容直接问审批（必须展示完内容再问）
- ❌ 用户选了"暂停"后继续推进

## 与现有技能的关系

| 技能 | HILT 位置 |
|------|----------|
| `closenai-brainstorming` | 完成后 → Gate 1 |
| `closenai-tdd` + `closenai-code-review` | 完成后 → Gate 2 |
| `closenai-verify` | 完成后 → Gate 3 |
