# ClosenAI Personal Model Domain Architecture

> Document: `01_PERSONAL_MODEL_DOMAIN_ARCHITECTURE.md`
> Version: V1.0
> Status: Engineering Baseline
> Date: 2026-10
>
> Strategic foundation:
>
> **Personal Model + Evidence + Pattern + Insight + Proactive + Outcome + Time**
>
> This document defines the domain boundaries, lifecycle, ownership rules, AI write boundaries, and invariants that the PostgreSQL schema and runtime must implement.

---

# 1. Executive Decision

ClosenAI's core domain is not:

```text
Journal
Memory
AI Chat
```

It is:

```text
Source Data
    ↓
Evidence
    ↓
Personal Model
    ↓
Pattern
    ↓
Insight
    ↓
Proactive
    ↓
Outcome
    ↓
Model Update
```

The most important architectural decision is:

> **AI is allowed to propose observations and derived knowledge, but AI is not the authoritative owner of the Personal Model.**

The authoritative state belongs to domain services.

Therefore:

```text
AI
    = inference / extraction / proposal

Domain Service
    = validation / policy / state transition / persistence

Database
    = durable source of truth
```

---

# 2. Domain Vocabulary

## 2.1 Source Data

Source Data is what the user actually supplied or what the product explicitly captured from an authorized source.

Examples:

- journal entry
- chat message
- voice transcription
- uploaded note
- explicit mood selection
- explicit goal
- explicit task completion
- explicit correction
- explicit feedback
- authorized external activity

Source Data is immutable after creation.

If the user edits content, do not silently mutate historical source semantics.

Use:

```text
original source
+
revision
```

where auditability matters.

---

# 3. PersonalModel

## 3.1 Definition

`PersonalModel` is the current, structured, user-specific representation of information that ClosenAI has enough evidence to treat as useful for future personalization.

It is NOT:

- a copy of all conversations
- a JSON blob containing everything the AI believes
- a personality diagnosis
- a psychological profile
- an LLM context window
- a collection of unverified assumptions

It contains only structured state that has passed the applicable domain rules.

---

## 3.2 PersonalModel Components

The model is composed of typed subdomains:

```text
PersonalModel
├── PersonalFact
├── Preference
├── Goal
├── Commitment
├── RelationshipReference
├── StateObservation
├── PatternReference
└── ModelMetadata
```

Not every component must be implemented in V1.

The minimum V1 set is:

```text
PersonalFact
Preference
Goal
Commitment
PatternReference
ModelMetadata
```

---

# 4. Fact vs Memory

This distinction is mandatory.

## 4.1 Memory

`Memory` means historical source information that may be useful to retrieve.

Examples:

```text
2026-09-12:
User said they were preparing for an exam.
```

Memory belongs to the source/history layer.

Memory does not automatically become a PersonalFact.

---

## 4.2 PersonalFact

A `PersonalFact` is a normalized, reusable proposition about the user that has enough evidence and/or explicit user confirmation to be used for personalization.

Example:

```text
Fact:
User is preparing for an exam.

Status:
confirmed

Source:
2026-09-12 entry
```

Another:

```text
Fact:
User prefers quiet environments when working.

Status:
confirmed

Evidence:
3 records
```

---

## 4.3 Rule

Never promote:

```text
one ambiguous statement
```

directly into:

```text
confirmed PersonalFact
```

Unless the user explicitly stated it as a fact.

For inferred facts:

```text
candidate
→ evidence
→ confirmation
→ active
```

---

# 5. Pattern

## 5.1 Definition

A Pattern is a time-bounded or recurring relationship observed across multiple pieces of evidence.

Pattern is NOT a personality label.

Bad:

```text
User is avoidant.
```

Better:

```text
Difficult conversations were postponed
in 3 observed situations over 60 days.
```

The second is an observable longitudinal pattern.

---

## 5.2 Pattern Requirements

A Pattern must have:

```text
pattern_type
scope
time_range
evidence_count
confidence
status
```

Optional:

```text
frequency
recurrence
change_direction
```

---

## 5.3 Pattern Lifecycle

```text
candidate
    ↓
observed
    ↓
supported
    ↓
confirmed
    ↓
active
    ↓
weakened
    ↓
expired / rejected
```

Not every pattern reaches `confirmed`.

### Candidate

Generated by detection.

### Observed

There is sufficient raw evidence to describe an observation.

### Supported

Evidence exceeds the minimum threshold.

### Confirmed

User confirms the pattern, or domain policy permits confirmation through repeated high-confidence observations.

### Active

Pattern remains relevant and usable.

### Weakened

New evidence reduces confidence or recurrence.

### Expired

Pattern is no longer recent/relevant.

### Rejected

User or policy explicitly rejects it.

---

# 6. Insight

## 6.1 Definition

An Insight is a user-facing interpretation derived from one or more Patterns, Facts, and/or Evidence.

Example:

```text
You seem to have handled high-pressure weeks
more effectively in the last two months.
```

An Insight is presentation-level.

It should NOT become the canonical Personal Model merely because an LLM generated it.

---

## 6.2 Insight Structure

Every meaningful Insight should reference:

```text
source evidence
+
supporting patterns/facts
+
time range
+
confidence
+
generation version
```

Minimum conceptual structure:

```text
Insight
├── statement
├── evidence[]
├── pattern[]
├── confidence
├── status
├── generated_at
└── model_version
```

---

# 7. Evidence

## 7.1 Definition

Evidence is the explicit provenance connecting a derived claim to the source material that supports it.

Evidence is not the same as Source Data.

```text
Source Data
    = what happened / what user said

Evidence
    = why a derived statement is allowed to exist
```

Example:

```text
Source:
Entry #102
"Had another difficult conversation and postponed it."

Evidence:
supports_pattern = P-001
role = supporting
strength = 0.8
```

---

# 8. Evidence Types

V1:

```text
direct
repeated
temporal
behavioral
user_confirmed
user_corrected
```

Recommended semantics:

### direct

User explicitly stated the fact.

### repeated

The same observation appears across multiple source records.

### temporal

Evidence supports a change across time.

### behavioral

Evidence comes from an explicitly recorded behavior/action.

### user_confirmed

User explicitly confirmed the derived statement.

### user_corrected

User explicitly corrected previous model state.

---

# 9. Evidence Rules

Evidence must be:

- traceable
- immutable as a historical relationship
- attributable to a source
- time-aware
- explainable
- removable from derived use if source becomes invalid

The system must be able to answer:

```text
Why does ClosenAI believe this?
```

and:

```text
Which user records support it?
```

---

# 10. Source Data vs Derived Data

## 10.1 Source Data

Authoritative:

```text
User input
Explicit user feedback
Explicit user correction
Authorized external source event
```

Source Data is never generated by an LLM.

---

## 10.2 Derived Data

Generated or computed:

```text
Entity extraction
Fact candidate
Pattern
Insight
Recommendation
Proactive candidate
Confidence score
Summary
Embedding
```

Derived Data must contain provenance.

---

# 11. AI Write Boundary

This is a hard architectural rule.

## 11.1 AI MAY write

AI may create proposals:

```text
FactCandidate
PatternCandidate
InsightDraft
EvidenceCandidate
ProactiveCandidate
Summary
Classification
Extraction
```

---

## 11.2 AI MAY NOT directly write

AI must not directly mutate:

```text
PersonalFact.status
Pattern.status
Goal.status
Commitment.status
User correction state
Safety state
Proactive delivery state
Outcome truth
Canonical PersonalModel state
```

---

# 12. Domain Service Responsibilities

## PersonalModelService

Responsible for:

- promoting facts
- changing fact status
- applying user corrections
- rebuilding model references
- model versioning

## EvidenceService

Responsible for:

- creating evidence links
- validating source references
- confidence policy
- evidence invalidation

## PatternService

Responsible for:

- candidate creation
- evidence aggregation
- confidence calculation
- state transitions
- expiry
- rejection

## InsightService

Responsible for:

- generating insight requests
- validating referenced evidence
- publishing/retracting insights

## ProactiveService

Responsible for:

- eligibility
- frequency caps
- safety checks
- delivery state

## OutcomeService

Responsible for:

- recording explicit outcomes
- linking outcomes to actions/proactives/goals
- triggering model re-evaluation

# 13. User Correction

User correction is a first-class domain event.

Examples:

```text
"This is not true."

"Partly true."

"That's outdated."

"That was a one-time thing."

"Remember this."

"Don't use this anymore."
```

A correction must NOT simply overwrite the old record.

Instead:

```text
Old Model State
      ↓
Correction Event
      ↓
Domain Validation
      ↓
New Model State
      ↓
Old State retained in history
```

This creates a durable audit trail.

---

# 14. Correction Semantics

V1 should support:

```text
confirm
reject
partially_confirm
outdated
correct
forget_from_model
```

Important:

`forget_from_model` means:

> stop using the derived knowledge for future personalization.

It does not necessarily mean deleting the original source record.

Data deletion and model invalidation are separate operations.

---

# 15. Pattern Confirmation

A Pattern can become confirmed through:

### Path A — explicit user confirmation

```text
Pattern candidate
→ user confirms
→ confirmed
```

### Path B — repeated high-quality evidence

Only if the configured policy allows automatic confirmation.

This policy must be conservative.

The system should prefer:

```text
observed
```

over:

```text
confirmed
```

when evidence is weak.

---

# 16. Pattern Rejection

If a user rejects a pattern:

```text
Pattern
→ rejected
```

The same evidence must not immediately recreate the same pattern.

Store a rejection signature:

```text
pattern_type
pattern_scope
user
```

with cooldown/version rules.

This prevents:

```text
AI:
"You often avoid X."

User:
"No."

AI next week:
"You may often avoid X."
```

---

# 17. Insight Lifecycle

```text
draft
 ↓
validated
 ↓
published
 ↓
acknowledged
 ↓
confirmed / corrected / dismissed
```

An Insight can also be:

```text
retracted
expired
```

if its supporting evidence is no longer valid.

---

# 18. Outcome

Outcome records what happened after:

```text
Goal
Action
Proactive
Insight
```

Example:

```text
Pattern:
User postpones difficult conversations.

Action:
User started the conversation.

Outcome:
Conversation went better than expected.
```

Outcome must be explicit whenever possible.

Do not infer:

```text
No follow-up message
=
Positive outcome
```

Absence of data is not an outcome.

---

# 19. Outcome → Pattern

Outcome can change Pattern confidence.

Example:

```text
Pattern:
Difficult conversations are usually postponed.

New Outcome:
User handled the latest conversation immediately.

Result:
Pattern frequency decreases.
Confidence may decrease.
Pattern remains active until sufficient evidence accumulates.
```

This is critical:

> Patterns are dynamic states, not permanent labels.

---

# 20. Personal Model Versioning

Personal Model needs two forms of versioning.

## 20.1 Logical Version

Each accepted model mutation increments:

```text
model_version
```

Example:

```text
user 42

version 18
→ add fact

version 19
→ confirm pattern

version 20
→ reject old pattern
```

---

## 20.2 Entity History

Do not overwrite previous state without history.

Use:

```text
valid_from
valid_to
status
```

where historical reconstruction is useful.

The system should support:

```text
What did we believe about this user on 2026-08-01?
```

---

# 21. Model Snapshot

A materialized snapshot may be generated for fast AI context:

```text
PersonalModelSnapshot
```

It is a derived cache.

It is NOT the source of truth.

Therefore:

```text
Database entities
        ↓
Model Builder
        ↓
Snapshot
        ↓
LLM context
```

Never:

```text
LLM context JSON
        ↓
overwrite database
```

---

# 22. Domain Invariants

The following must be enforced.

### Invariant 1

No Insight without traceable support.

### Invariant 2

No Pattern without evidence.

### Invariant 3

No confirmed inferred Fact without confirmation or explicit policy.

### Invariant 4

No Proactive delivery without eligibility validation.

### Invariant 5

No Outcome inferred solely from silence.

### Invariant 6

User correction always creates an auditable event.

### Invariant 7

AI cannot bypass domain services.

### Invariant 8

Derived data must identify its generation/model version.

### Invariant 9

Deleted/invalid source evidence must invalidate dependent derived claims according to policy.

### Invariant 10

Safety policy overrides personalization.

The domain should emit events such as:

```text

pattern.weakened

insight.confirmed
insight.corrected
insight.dismissed
proactive.created
proactive.sent
proactive.responded
outcome.recorded
model.updated
```

Events are for:

- asynchronous pipelines
- analytics
- audit
- rebuilding
- downstream services

They are not the canonical database itself.

# 25. LLM Failure Containment

LLM output must be treated as untrusted derived input.

Validate:

```text
schema
source references
allowed entity types
confidence range
time range
evidence existence
safety policy
language policy
evidence policy
```

Reject malformed or unsupported output.

---

# 26. What Becomes the True Personal Model

The Personal Model should answer:

```text
What do we know?
Why do we believe it?
How confident are we?
When was it last confirmed?
What changed?
What is currently active?
What did the user correct?
What outcomes have occurred?
```

If the system cannot answer these questions, it does not yet have a real Personal Model.

---

# 27. V1 Scope

Implement first:

```text
SourceRecord
PersonalFact
Evidence
Pattern
Insight
UserFeedback
Outcome
PersonalModelVersion
```

Defer:

```text
Relationship graph
advanced ontology
external context ingestion
predictive models
complex personality systems
large knowledge graph
```

The architecture must allow them later without requiring them now.

---

# 28. Final Architecture Principle

The core principle is:

> **ClosenAI remembers source data, maintains a validated Personal Model, derives Patterns from Evidence, renders Insights from those Patterns, proactively follows up when policy permits, and uses Outcomes to update the model over time.**

The moat is not the number of memories.

The moat is:

```text
Validated Personal Model
×
Evidence
×
Feedback
×
Outcome
×
Time
```
